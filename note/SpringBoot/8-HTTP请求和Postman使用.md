# SpringBoot：HTTP协议与Postman的使用

## 一、URL组成结构

完整URL是网络资源的统一访问地址，由多个核心部分组成，各部分各司其职，规范网络资源访问规则。

示例地址：`https://example.com:80/blog?searchtest&sort_by=created_at#header`

- **Domain（域名）**：服务器的访问地址，如域名、IP地址、localhost本地地址
- **Port（端口）**：服务器服务端口，默认HTTP为80端口
- **Path（路径）**：服务器资源访问路径，定位具体接口或页面资源
- **Query Parameters（查询参数）**：URL中`?`后的键值对参数，用于传递请求条件
- **Fragment/Anchor（锚点）**：以`#`开头，用于定位网页内部指定区块，仅作用于前端页面，不向服务器传递数据。例如 `example.com/about#team`可直接跳转至about页面的team板块

## 二、HTTP协议基础

### 2.1 协议定义

HTTP 全称超文本传输协议，是**基于请求与响应模型的应用层协议**，也是互联网数据交互的核心规范。

### 2.2 核心作用

统一规定客户端（浏览器、Postman、APP）与服务器之间的信息传递格式与规则，是两端数据交互的通用标准，所有HTTP通信都必须遵守该规范。

### 2.3 报文整体结构

HTTP通信分为请求报文和响应报文两部分，结构相互对应：

- **HTTP请求**：客户端向服务器发送数据，由**请求行、请求头、请求体**三部分组成
- **HTTP响应**：服务器向客户端返回数据，由**状态行、响应头、响应体**三部分组成

## 三、HTTP请求详解

![image-20260810104408073](./../assets/7-HTTP%E8%AF%B7%E6%B1%82%E5%92%8CPOSTMAN%E4%BD%BF%E7%94%A8/image-20260810104408073.png)

### 3.1 请求行

- **位置**：请求报文的第一行
- **组成格式**：请求方法 + 资源访问路径 + HTTP协议版本
- **示例**：`POST /user/login HTTP/1.1`
- **常用请求方法**：        
  - **GET**：从服务器获取资源，无请求体，参数一般拼接在URL后
  - **POST**：向服务器提交数据，新建资源，支持请求体传参
  - **PUT**：更新服务器已存在的资源
  - **DELETE**：删除服务器指定资源

### 3.2 请求头

- **位置**：请求行下方、空白分隔行上方
- **格式**：键值对形式，每行一组参数，用于告知服务器客户端的请求信息
- **核心字段 Content-Type**：定义请求体的数据格式，是接口传参的核心配置，常见取值：        
  - `text/html`：HTML网页格式数据
  - `image/jpeg`：JPG图片格式资源
  - `application/json`：JSON结构化数据（前后端主流传参格式）
  - `application/x-www-form-urlencoded`：普通表单默认提交格式
  - `multipart/form-data`：支持文件上传的表单格式
- **其他常用请求头**：        
  - `User-Agent`：客户端标识（Postman、浏览器等）
  - `Accept`：客户端期望接收的数据格式
  - `Host`：目标服务器地址与端口
  - `Accept-Encoding`：客户端支持的数据压缩格式
  - `Connection`：连接状态（keep-alive 保持长连接）
  - `Content-Length`：请求体数据字节长度
  - `Cookie`：客户端会话缓存信息

### 3.3 请求体

- **位置**：请求头空白分隔行之后
- **作用**：承载客户端向服务器传输的核心实体数据
- **使用场景**：主要用于 POST、PUT 请求，GET 请求无请求体
- **配套配置**：需配合 Content-Type、Content-Length 请求头使用
- **示例数据**：`name=zhangsan&password=123`
- **注意**：请求报文可根据业务需求，不携带请求体数据

## 四、HTTP响应详解

![image-20260810104436409](./../assets/7-HTTP%E8%AF%B7%E6%B1%82%E5%92%8CPOSTMAN%E4%BD%BF%E7%94%A8/image-20260810104436409.png)

### 4.1 状态行

- **位置**：响应报文第一行
- **组成格式**：HTTP协议版本 + 状态码 + 状态描述
- **示例**：`HTTP/1.1 200 OK`
- **状态码分类**（三位数字，首位数字定义响应类型）：        
  - **1XX 信息提示**：临时响应，极少用于业务开发
  - **2XX 请求成功**：服务器正常处理请求，典型：200（请求成功）
  - **3XX 重定向**：资源跳转，典型：302（临时重定向）
  - **4XX 客户端错误**：请求参数或地址异常，典型：404（资源不存在）、400（参数错误）、405（请求方法不支持）
  - **5XX 服务端错误**：服务器代码或服务异常，典型：500（服务器内部错误）

### 4.2 响应头

- **位置**：状态行下方、空白分隔行上方
- **格式**：键值对形式，用于描述服务器返回数据的附加信息
- **常用字段**：        
  - `Content-Type`：服务器返回的数据格式
  - `Transfer-Encoding`：数据传输编码方式
  - `Date`：服务器响应时间
  - `Keep-Alive`：长连接超时时间
  - `Connection`：连接状态

### 4.3 响应体

- **位置**：响应头空白分隔行之后
- **作用**：承载服务器返回的核心业务数据
- **数据类型**：支持 JSON、XML、HTML、图片、二进制文件等多种格式
- **示例（JSON响应）**

```json
{
    "code": 0,
    "msg": "登录成功",
    "data": null,
    "ok": true
}
```

## 五、Accept与Content-Type的区别

![image-20260810104503468](./../assets/7-HTTP%E8%AF%B7%E6%B1%82%E5%92%8CPOSTMAN%E4%BD%BF%E7%94%A8/image-20260810104503468.png)

两个字段均用于定义数据格式，核心区别在于**作用方向、出现位置**不同，是接口调试的重点知识点。

### 5.1 Accept

- **出现位置**：仅存在于**请求头**
- **核心含义**：客户端主动声明，自己**希望接收**的数据格式
- **示例**：`Accept: application/json`，表示客户端要求服务器返回JSON格式数据

### 5.2 Content-Type

- **出现位置**：**请求头、响应头均可存在**
- **核心含义**：声明**当前发送方传输的实体数据格式**
- **场景说明**：        
  - 请求中：客户端告知服务器，本次提交的参数数据格式
  - 响应中：服务器告知客户端，本次返回的结果数据格式
- **示例**：`Content-Type: application/json`，表示发送方传输的是JSON格式数据

## 六、Postman请求Body格式详解

Postman 支持5种请求体提交格式，不同格式对应不同数据场景和后端适配规则，是接口测试的核心操作点。

### 6.1 form-data

![image-20260810104611191](./../assets/7-HTTP%E8%AF%B7%E6%B1%82%E5%92%8CPOSTMAN%E4%BD%BF%E7%94%A8/image-20260810104611191.png)

- **格式特点**：表单格式提交，支持文本参数 + 文件上传
- **自动请求头**：`multipart/form-data`
- **后端适配规则**：接口不能添加 `@RequestBody` 注解，否则参数接收失败
- **适用场景**：图片、压缩包、文档等**文件上传接口**

### 6.2 x-www-form-urlencoded

![image-20260810104629436](./../assets/7-HTTP%E8%AF%B7%E6%B1%82%E5%92%8CPOSTMAN%E4%BD%BF%E7%94%A8/image-20260810104629436.png)

- **格式特点**：以 `key=value&key2=value2` 键值对拼接格式提交
- **自动请求头**：`application/x-www-form-urlencoded`
- **后端适配规则**：接口不能添加 `@RequestBody` 注解
- **适用场景**：普通表单提交、简单键值对参数接口（如普通登录接口）

### 6.3 raw

纯文本自定义格式，可手动切换数据类型，自动匹配对应 Content-Type，是前后端分离项目主流格式。

- text：对应 `text/plain` 纯文本格式
- javascript：对应 `application/javascript`
- **json（重点）**：对应 `application/json`，用于传递JSON结构化参数
- html：对应 `text/html`
- xml：对应 `application/xml`

**后端适配规则**：使用JSON格式传参时，接口**必须添加 @RequestBody 注解**，否则接口报错、参数无法接收

**适用场景**：所有JSON格式交互的业务接口（主流开发场景）

### 6.4 binary

- **格式特点**：纯二进制流传输，无键值对结构
- **自动请求头**：`application/octet-stream`
- **限制**：单次只能上传一个文件，无法携带文本参数
- **适用场景**：极少使用，仅用于纯二进制文件直传场景

### 6.5 GraphQL

专用查询语言格式，常规业务接口测试几乎不使用。

## 七、Postman Query Params与Body的区别

### 7.1 Query Params（URL参数）

- **传参方式**：参数拼接在URL地址 `?` 后面，格式：`url?key1=value1&key2=value2`
- **核心特点**：参数暴露在地址栏，无请求体
- **适用请求**：优先搭配 GET 请求使用，用于简单条件查询

### 7.2 Body（请求体参数）

- **传参方式**：参数存放在请求体中，不展示在URL地址栏
- **核心特点**：参数隐蔽，支持大量数据、文件、JSON结构化数据传输
- **适用请求**：POST、PUT、DELETE 等请求

## 八、Postman 常用调试技巧

- **报文查看**：请求发送后，可查看完整 Request Headers（请求头）、Response Headers（响应头）、响应体数据，快速定位参数、格式错误
- **Console控制台**：底部控制台可打印完整请求日志，支持格式化展示报文，用于接口调试排错
- **Collections 集合**：分类管理项目所有接口，批量保存、复用、分享接口测试用例
- **Environments 环境变量**：统一配置域名、端口、Token等公共参数，一键切换测试、正式环境
